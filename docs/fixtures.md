# Synthetic data spec

All data is generated by our own seed script from a fixed RNG seed. Nothing private, nothing
scraped, nothing login-protected (rule 6). Re-running the seed produces a byte-identical graph,
which matters because the cold-vs-warm cost comparison is only honest if both runs see the same
world.

**Deliberately not building an ingestion pipeline.** Judges score the agent, not our ETL. Any
hour spent on a Datadog connector is an hour not spent on the memory graph.

## Topology

| Thing | Count | Shape |
|---|---|---|
| `Service` | 40 | 6 tier-1 (edge/customer-facing), 14 tier-2, 20 tier-3 (infra/data) |
| `DEPENDS_ON` | ~95 | Layered DAG, tier-1 → tier-2 → tier-3, plus ~8 same-tier edges. ~30% marked `critical`. |
| `Person` | 12 | Each owns 2–5 services; every service has a `primary`, ~half have a `secondary` |
| `Commit` | ~200 | Over a simulated 14-day window; `files` drawn from the owning service's `paths` plus 15% cross-service noise |
| `Deploy` | ~60 | 1–6 commits each, touching 1–3 services |
| `Alert` | ~80 | Controlled metric vocabulary; clustered in time around bad deploys |
| `Incident` | ~60 | Historical, resolved, `verified: true` — this is the memory's starting corpus |
| `FailureMode` | 8 | `connection_pool_exhaustion`, `cache_stampede`, `n_plus_one_query`, `thread_starvation`, `disk_pressure`, `clock_skew`, `retry_storm`, `schema_lock` |
| `Runbook` | 8 | One per failure mode |

Directional convention, fixed here so nothing downstream guesses: **`(caller)-[:DEPENDS_ON]->(callee)`**.
A tier-1 API depends on a tier-3 database, so the edge points API → database. Day 1's first
verification is a hand-drawn 5-node subgraph checked against both `upstream_candidates` and
`blast_radius`.

No disconnected components — `algo.WCC` over `DEPENDS_ON` must return a single component id. An
unreachable service would make a demo query return nothing for reasons that look like a bug in
the agent.

## The three scenario classes

The memory story has nothing to chew on unless the data contains all three. Each one has to be
injectable by name from the demo script.

### A — repeated shape (the money shot)

At least **8** historical incidents sharing one signature: tier-1 service, `latency_p99` alert,
high fan-in, upstream deploy inside the window, severity `high`. They sit on *different
services*, so the alert texts are unrelated and only the structure matches.

Two of these are held back from the seed and injected live during the demo. The first runs cold
and writes the plan; the second recalls it. This pair *is* the Track 02 claim — if only one thing
in the fixture set works, it has to be this.

Target: cold ≈ 12–15 tool calls, warm ≈ 3–5, same culprit commit, cost ratio ≥ 5×.

### B — novel shape (the cold path still works)

One incident with a signature appearing nowhere in history: a tier-3 service, `queue_depth`
alert, **no** deploy in the window — so the cause is not a code change at all but an upstream
`saturation` cascade. `recall_plan` returns nothing, the agent investigates from scratch, and the
correct answer is "no culprit commit; the cause is structural" with the path to the saturated
dependency.

An agent that cannot say "not a deploy" will confidently blame a commit. This scenario exists to
prove it doesn't, and the fixture is built so the honest answer is checkable.

### C — the plan that was wrong (memory records failure)

A historical plan with `runs: 4, successes: 2`, already `SUPERSEDED_BY` a corrected plan, with a
`Tool-[:FAILS_ON]->Condition` edge recording *why*: `suspect_commits` ranked by file overlap in a
case where the culprit commit touched a shared library and had near-zero overlap with the failing
service's own paths.

This is the scenario most entries will not have. "Our memory stores what didn't work, and the
graph shows which tool misled it" is a stronger claim than any success metric, and it is a
one-query demo: show the superseded plan and the condition edge.

## Generator rules

- Seeded RNG, seed recorded in the module and in the README.
- Commit `files` drawn from the owning service's `paths`, with 15% cross-service noise. The noise
  is what makes `overlap` a non-trivial ranking signal rather than a lookup.
- Alerts cluster 0–45 min after a bad deploy; ~20% of alerts are noise with no related deploy, so
  the agent must tolerate a window with nothing in it.
- `Service.betweenness` pre-computed once at seed time via `algo.betweenness` and stored, used as
  a tie-break in `upstream_candidates`.
- Timestamps relative to seed time, not absolute, so the fixture does not rot between Day 1 and
  the demo.

## Verification (Day 1 exit criteria)

Before any agent code exists:

- node and edge counts match the table above
- `algo.WCC` over `DEPENDS_ON` returns one component
- the hand-drawn 5-node subgraph matches `upstream_candidates` and `blast_radius` output
- every scenario class is retrievable by signature
- scenario A's eight incidents share exactly one signature value
